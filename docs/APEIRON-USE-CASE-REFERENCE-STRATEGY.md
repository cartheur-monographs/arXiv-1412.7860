# Apeiron Use-Case Reference Strategy

## Purpose

This note evaluates whether the current `arXiv-1412.7860` paper can be
reframed as a use-case paper for `Volatco Apeiron`, and if so, how that should
be done without weakening technical credibility.

Date: `July 26, 2026`

## Short Answer

Yes, it is possible to reposition the paper as an `Apeiron-first` use-case in
the `Volatco` line, but not by updating the bibliography alone.

The current paper can support that repositioning because it already contains:

- a local geometric partitioning model
- bounded addressability and traversal logic
- a claim about finite computational data-space
- an emphasis on autonomous organization rather than cloud orchestration

Those traits align naturally with `Apeiron` as a substrate story for:

- deterministic local behavior
- bounded autonomy
- low-power persistent operation
- event-driven or asynchronous embedded execution

What the current paper does **not** yet provide is a direct contemporary
systems interpretation. That means the correct move is:

1. keep the original concept
2. reinterpret it through the `Apeiron` substrate framing
3. add bounded modern references and use-case framing
4. avoid pretending the original text itself already demonstrated `Volatco`

## Core Positioning Judgment

The paper is a better fit for `Volatco Apeiron` than for the `Continuum`.

Reason:

- the current manuscript is fundamentally about one bounded structure
- its logic is local rather than distributed
- its strongest modern interpretation is as a compact substrate or node model
- scaling is only implicit, not central

This matches the `AI4SME` guidance that `Apeiron` should lead when the story
is:

- compact
- embedded
- low-power
- local
- deterministic

So the clean framing is:

`Volatco` is the public platform identity. This paper is an
`Apeiron-first` architecture/use-case paper that interprets the geometric
partitioning model as a local substrate for bounded embedded intelligence.

## Important Constraint

The `AI4SME` markdown notes are excellent architectural source material, but
they are not ideal as formal references in an arXiv paper unless they are made
public and citable in a stable form.

That means they should currently be treated as:

- editorial source documents
- internal architecture baselines
- wording and positioning guidance

They should **not** be the primary visible scholarly references in the
manuscript unless they are separately published as stable public monographs,
technical notes, or white papers.

## Recommended Reference Policy

Use a two-layer reference strategy.

### Layer 1: Internal editorial basis

Use these materials to drive the rewrite:

- `AI4SME/platform/apeiron-and-continuum.md`
- `AI4SME/platform/application-distinctions.md`
- `AI4SME/ai4sme/technical-evidence.md`

These should shape:

- section structure
- terminology
- use-case emphasis
- constraints language
- the distinction between `Apeiron` and the `Continuum`

### Layer 2: Formal outward references

In the manuscript itself, keep or add references that support:

- computational geometry
- automata or reconfigurable computation
- edge or embedded local control
- asynchronous or event-driven computation
- bounded autonomy and resilient local behavior

This keeps the paper citable and externally legible while still allowing the
`Volatco Apeiron` interpretation to be explicit in the prose.
